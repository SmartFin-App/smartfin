SmartFin — Alpha Test01 / 15
Problem statement

Thai users already have a record of every payment. It is trapped in their photo gallery.

1 · Manual entry fails

Budgeting apps depend on the user typing each expense. People abandon this within weeks, so the data is incomplete exactly when advice would matter.

2 · No bank aggregation

Thailand has no consumer open-banking API. Services like Plaid do not cover Thai retail banks, so automatic transaction import is not available to a student project.

3 · Generic advice

Chatbot finance tools answer from general knowledge. They cannot say what this user spent on food this month, because they never see the data.

The opening. Every PromptPay, K PLUS, SCB EASY, Krungthai NEXT and Bangkok Bank transfer ends in a confirmation slip the user screenshots. The record already exists — it is simply an image. SmartFin turns that image into structured data, then lets an AI agent reason over it.
SmartFin — Alpha Test02 / 15
Target user & use cases

Who it is for, and what they can do

Primary user

A Thai working adult or student who pays by PromptPay several times a day, keeps every confirmation slip in their gallery, and has abandoned at least one budgeting app.

Design consequences

  • Currency is integer Thai Baht (฿) end-to-end — no floats, no decimals.
  • Slips print Buddhist-era years: 2569 → 2026 conversion is required, not optional.
  • Merchant names arrive in Thai script and are transliterated on extraction.
  • Month boundaries are pinned to UTC+07:00, not server time.
SmartFin — Alpha Test03 / 15
Scope

What the project commits to — and what it deliberately excludes

In scope

  • Slip & receipt capture — camera capture and automatic gallery detection, extracted by a vision model.
  • Transaction ledger — create, list, edit, delete; manual entry as a fallback path.
  • Monthly budgeting — income, budget limit, category breakdown, per-month summaries.
  • Agentic AI Coach — answers grounded in the user's own records, and able to act on them.
  • Savings goals — set by the user or by the coach, with progress derived from actual months.
  • Account management — profile, photo, credentials, account deletion.

Out of scope

  • Direct bank integration — no consumer open-banking API exists in Thailand; the slip is the integration.
  • Moving money — SmartFin never initiates a payment or transfer. It is read-and-advise only.
  • Investment or tax advice — the coach redirects to general financial health.
  • Multi-currency — Thai Baht only, which is what makes integer money safe.
  • Multi-user or shared budgets — one account, one person.
  • iOS release build — Android is the delivery target for this milestone.
Why the boundary sits here. Every excluded item either requires a commercial banking agreement or moves the project from advice to financial transactions, which carries a regulatory burden a one-semester project cannot honestly meet.

SmartFin — Alpha Test11 / 15
Demonstration

Demo flow — one continuous story, following the use cases

Sign in and set up the profile. Income bracket, status and financial health — the same values the coach is later grounded in. UC: Manage profile
Pay by PromptPay, return to the app. The gallery watcher offers the new slip unprompted. UC: Auto-detect new slips
Confirm the extracted entry. Merchant, ฿ amount and date come back from the vision model; the user corrects the category and saves. UC: Review & confirm
Watch the dashboard react. Budget ring, category breakdown and savings tracker all move on the same figure. UC: Track budget
Ask the coach a real question. “Can I afford ฿5,000 more this month?” — it calls its own tools and answers from the ledger. UC: Ask the AI Coach
Let the coach act. “Set aside ฿50,000 for a Japan trip.” The goal is written, and the dashboard tracker updates. UC: Ask the AI Coach

What the flow is designed to prove

  • The user never types an amount from step 2 onward.
  • The coach reads this user's records, not general knowledge.
  • The coach writes as well as reads — step 6 changes stored state.
  • One figure moves consistently through capture, budget and goal.

Fallback if the network fails

A seeded demo account with six months of Thai transactions is loaded in advance, and a sample slip image ships with the app — so steps 3 to 6 can be shown without a live payment.

SmartFin — Alpha Test12 / 15
Engineering quality

What we found when we audited the build

Before this milestone the codebase was reviewed end to end — backend logic, client behaviour, and the contract between them. The defects worth reporting were not in the AI features; they were in the arithmetic underneath them.

Representative defects, now fixed

  • Stale monthly cache. The refreshed summary was never written back, so the dashboard and the coach could report different totals for the same month.
  • Timezone freeze. A month could be frozen at ฿0 when the phone and a UTC server disagreed about the date at midnight.
  • Backdated entries invisible. Adding a forgotten expense to a closed month never invalidated that month's totals.
  • Receipts lost on failure. A slip was marked processed before the scan ran, so a failed scan hid it permanently.

How they were prevented from recurring

  • Month boundaries and cache invalidation moved into internal/summaries — one implementation, used by handlers and agents alike.
  • 13 unit tests now pin the month arithmetic, the partial-update contract and the agent's tool list.
  • Profile updates bind to a typed request struct, so an unknown field can no longer be written into the user document.
  • Single-transaction routes are scoped by owner, closing an ID-guessing path.
Why this belongs in the presentation. The AI layer is the visible part of the project, but its answers are only as trustworthy as the ledger beneath it. A coach that confidently quotes a stale number is worse than no coach at all.

The claim being demonstrated

A Thai user can go from paying by PromptPay to seeing that payment reflected in their budget, their category breakdown and their savings goal — without typing a single number — and can then ask an agent that reads and writes their real records what to do about it.

Known limitations, stated plainly

  • The API does not yet verify identity tokens.
  • The backend runs locally; it is not deployed.
  • Client test coverage is manual.
  • Two secondary screens remain unbuilt.
